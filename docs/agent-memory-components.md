# pocketBrain and the components of agent memory

Anthropic's research post [The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory) (read 2026-11-07) describes memory as a hierarchy of four layers with an offline pass, "dreaming", that moves material between them. This page maps each layer onto pocketBrain's code on `main` and says where pocketBrain matches, where it differs on purpose, and what it lacks. Line numbers are as of commit `067bb83`.

## Whose memory it is

The post is about an agent's own working memory. Claude plays a game or answers questions about a database across sessions, writes notes for itself, and gets better at that task. The memory belongs to the agent, the truth it is checked against is the agent's own transcript, and "learning" means the agent improves at the work.

pocketBrain is a person's memory, owned by the person and shared by every assistant they use. Its truth is the person's word and the sources they connect (mail, calendar), not any assistant's transcript. It learns about the person; it does not teach an assistant to do a task better. The post's hierarchy describes what happens inside one assistant. pocketBrain sits one level above that, as the store several assistants read from and write into, and it checks their private memories against itself (`src/memsync.ts:1`).

What this means for the pitch: the post confirms that the shape is right (a small injected top, notes, linked wiki pages, an event log, a nightly pass that corrects and organises). It does not say that a person needs a memory owned outside the vendor. That is pocketBrain's claim, and the post leaves it open. Say "the memory layer the research describes, owned by you instead of by each assistant," not "what Anthropic is building."

## Where pocketBrain differs on purpose

- **One memory, many agents.** The post's memory lives inside one agent. pocketBrain is the one store all of a person's assistants use, each seeing only its carved slice, and it compares what each assistant remembers privately with the brain (`src/memsync.ts:1`).
- **The hub is the source of truth, not a transcript.** In the post the transcript is ground truth. In pocketBrain an assistant's transcript is only that assistant's account; the truth is the owner's word or a verified source, in that order.
- **Everything files itself, and the owner is asked only on conflict.** The post lets the model decide what is salient. pocketBrain files what a source states by rule (`src/filing.ts:1`) and asks the owner only when two values cannot both hold.
- **Models suggest and never settle.** Dreaming in the post rewrites notes on its own. The Gardener may only rewrite page text from facts already held; a new or contradicting value is a proposal or a conflict, and the owner's answer is final (`src/tend.ts:80`).
- **Nothing is injected that could be wrong in every session.** The post warns that a wrong injected note spreads to every session. pocketBrain avoids the risk by injecting rules only and serving facts on request, with their freshness and source attached.

## Candidate additions, ranked by value to the owner

The scope freeze runs to about 2026-11-30. Nothing new is built before then unless the owner asks.

1. **A small "about you" block every assistant starts with (after freeze).** The post's top layer: the owner's few most-used, owner-confirmed facts (name, ties, current projects), cut to each assistant's view, sent with the contract instead of waiting for a `context_pack` call. Only owner-confirmed or source-verified facts qualify, which answers the post's warning about wrong notes spreading. Value: every assistant knows the owner from the first message, even one that forgets to call the brain.
2. **A learning run beside the Gardener (after freeze).** Today's Gardener tends what the brain already holds: it checks facts at their source, weighs conflicts, syncs pages and forgets (`src/tend.ts:77`). A learning run would look at what happened instead: the hub's journal lines and the owner's own corrections and settles in the diary (`src/diary.ts:20`), and later the archived assistant logs (`src/logs.ts:1`). It would do two jobs the nightly pass does not. First, check a fact cited as `agent:<name>` against the log of the conversation it came from, which `verify_source` cannot do today (`src/core.ts:1414`); this is the post's "correct notes against the transcript". Second, find durable facts said in passing across conversations. Journal consolidation already does a narrow form of the second job on the hub, with an exact quote per fact (`src/sleep.ts:201`).

   How it would be bounded, all in code: it is a separate deployment of the Gardener role, like the web-only run (`src/tend.ts:69`), so the same hours, daily cap and run record apply. Its tools are reads, `remember` and `log_session`: no `wiki_sync`, no `suggest_answer`, no retire. Every fact it writes quotes one log or journal line word for word and cites it, so a pattern guessed across sessions with no line that states it is never written. A fact that contradicts a held value is a conflict for the owner, as for any writer. It starts report-only, as every new scheduled step does. Raw logs stay on the hub, because they hold whole conversations: the hub picks the candidate lines and sends only those, so the cloud run never reads a transcript.

   The risks: a guess about the owner filed as the owner's preference; an assistant's mistake learned and then repeated to every other assistant (the post's warning about wrong notes spreading); and volume, since the post's weakest run wrote 413 memory files and its best about ten, which argues for a small daily cap. Value: fewer facts an assistant misheard, and things the owner said once in a conversation stop being lost.

3. **Measure whether wiki pages improve answers (before freeze, only if the owner asks; it is an eval, not a feature).** The post found wiki plus search beat search alone (61% against 53%) only on questions that need several documents. Run the same comparison on the demo brain: `context_pack` with and without page text, graded on single-page and multi-page questions. Value: evidence for the wiki work, and a number to quote.
4. **Steer the Gardener by purpose rather than a fixed recipe (after freeze).** The post found fixed rules about what to write hurt stronger models. The nightly prompt (`src/tend.ts:77`) is a nine-step recipe. The hard limits already live in code (caps, `wiki_sync` refusals, conflicts never settled), so the prompt could state the goal and keep only the steps code cannot enforce. Needs the agents evals green before and after. Value: better pages and suggestions from the same nightly cost.
5. **Spend the nightly checks where the owner reads (after freeze).** The read log already knows which notes assistants are handed (`src/sleep.ts:92`). Using it to order `verify_source` calls, most-read facts first, matches the post's idea of tuning dreaming by access. Value: the facts most often repeated to the owner are the ones most often checked.
