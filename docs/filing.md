# Filing: what the hub decides alone

The owner is asked only about conflicts (owner, 2026-10-25; outside review v5). Everything else a capture or a source finds files itself on the hub's tick, with Undo, and an outside assistant's unanswered proposal expires. The code is `src/filing.ts`; conflicts are asked on the home and settled on `/settle/<id>` ([owner-home.md](owner-home.md)).

What is still open and isn't a conflict (an assistant's proposal, held mail, a held capture) waits on Settings (`/overview`). What the home counts there sits under **Needs a look** (`/overview#needs`, where the home's **Open Settings** lands), each with its own taps; the rest (requests, alerts, proposals that file or expire on their own) is under **Also here**, not counted (G705).

## When the hub decides
The text channel's tick inside `pocketbrain start` (every 5 minutes) reads your replies first, then runs `runAuto` on the server's write queue, one write at a time with everything else the hub writes, and under the decide lock below. Anything you answered in that tick is skipped, even a reply that couldn't apply, so a text of yours is never overruled a moment later. A tick run on its own (`textline watch` or cron `textline once` beside the server) never decides for you. The hub decides two kinds of item:

- **An outside assistant's proposal** whose `proposal_days` have passed is rejected (moved to `inbox/decided/`), by `auto-decide`. Rejecting only leaves the brain as it was; the assistant can propose it again.
- **A low-risk fact your calendar or mail proposed** (a pull's proposal, see "Saved for you" below) is saved on the next tick, by `auto-decide`, up to `source_saves_per_day` a day, once you turn that on (it is off by default).
- It never expires a proposal that is private or money, reads like health, legal or money (English or French, on any note), cites your own word (your message, your texts, your notes, or one waiting on `owner_message_registered`), came from your own material (captures, imports, the Gardener), or whose assistant is paused, read-only or no longer in the policy. Settings says why in one line.
- **Conflicts always wait for you.** What makes a side look stronger (verified, its date, which message it cites) is written by the assistants themselves, and the hub can check that a cited message exists but not that it says what the side claims. So it never picks.

Every decision is a line in `log/auto-decisions.jsonl`, a line in the next digest, and a row in Settings' "Filed for you this week" list with an Undo button (a conflict it filed is asked on the home, never listed there). Undo reverts the hub's commits as you. For an expiry that touches only the inbox, so it works whatever changed on the note since; for a saved fact it also takes the fact back out (if a later change touched the same lines, Undo says so and you fix it on the fact's page). The item comes back to Settings and the hub never decides that item again. The page's text is written again from its facts after every Undo, so it never goes on saying the undone value (G527; before, a clean revert left the page writer's sentence in place).

### File everything (only a conflict asks)

The owner's rule (2026-10-25): a fact is asked about only when it conflicts. This is the default, with or without rules/escalation.yaml: `pocketbrain filing all off` writes `auto_decide: { file: ask }` (committed as you), so each fact waits on Settings' Needs a look list, and `pocketbrain filing all on` takes it back. The hub files on its own tick, once a minute in its write queue (`fileTick` in `src/start.ts`), whether or not the text channel is set up (without the channel the tick only files: an assistant's proposal never expires and no source save runs). A new brain's rules/policy.yaml has the hub's own `capture` agent, inside the wall (no token, nothing connects as it): what its sources and captures find is written as it (`captureAgentName` in `src/rules.ts`; an owner's channel or resolver, when named, comes first). Then every fact a capture or a source pull proposed (a proposal with the `capture:` field only the capture pipeline writes, from the capture agent or from you, so the owner's own channel, your own captures and the pulls; the capture agent's own fact about you, written as an assistant, files too, on your own page, while that agent is active and unless it is private, money, health, legal or cites your word (other assistants' facts about you still ask); another agent allowed to capture keeps its own rule) files itself on the hub's next tick, by `auto-decide`, with no daily cap: on a person's page, as a new page, private, money, health or legal alike (each lands at its own tier, and neither the "Filed for you" line nor Recent updates prints a private value), and what you said through your own channel stays your word. A fact whose subject the model guessed files too, marked `confidence: inferred`, so `pocketbrain audit trust` lists it as guessed. It waits for you only when (`fileVerdict` in `src/filing.ts`):

- it is a fact already in conflict;
- it changes a value you confirmed with one dated the same day or later: that is a conflict, asked at once (one dated before your word asks nothing: it files to the fact's history and the "Filed for you" row says "kept your word", see "Older sources never re-ask" in [owner-home.md](owner-home.md));
- it would start a new page whose name now fits a page you have as well as a new one (the write path asks "new or same as …?"; a name that fits one note exactly is weighed against that note, as the write path would land it there). The hub never guesses which: it waits on Settings, and the north star counts it as an ask, with its own `held_by_ambiguity` line saying why (G603; one counted list since audit v10, G618). At the hub's start, a decided copy by such a name stays decided when a page it fits holds its fact from that copy's own source (a namesake page holding the same value doesn't count);
- it gives a different value for a fact the brain holds: that is a conflict, filed as one and asked once the Gardener has been by (below);
- it retires something, or it is a question.

#### An assistant's own proposals: held until a day, or set aside

A core assistant's own proposal that the rules above don't file (the capture agent writing as an assistant, a core writer outside its area or above its level, or a fact from its own memory imported with `pocketbrain memsync import` or sent as its `memory_dump`, G587) is held only while you hold your assistants' proposals: `auto_decide: { hold_assistants_until: YYYY-MM-DD }` in `rules/escalation.yaml`, none by default (it was a date in the code until 2026-10-30, G531; a value that isn't a date means no hold). The first tick it is held writes one diary line ("Something new about Jane Roy, held until Fri 30 Oct", never the value) in one hub commit with a `Why:` line. It is not an ask: the home, the north star and Settings' count leave it out. From that day it files by the rules above: on its page with Undo, a private one under the serving hold, a different value as a conflict to settle. One the write path handed back because the assistant can't see all of the page (a fact shared away from it, or a private record: `not_in_your_view`, invariant 3) waits for you instead, never as a plan the hub retries; when its value differs from the live one the home lists it as a conflict to settle (G598). One a write check sent to you (a value that reads like an instruction to an assistant, a source that is only a link the hub can't open, a claimed approval without your message on record) waits for you the same way: the hub's yes would be the assistant's write again and the check would hand it back (G599). A proposal that names its page by title is weighed against the page the write would land on: only pages its assistant can see, as `write()` resolves the name, so a namesake page hidden from that assistant is neither a conflict nor where the fact goes. When the hub's yes still comes back as a new proposal (a write check the assistant's write fails, such as a category it isn't given), the row says "left it for you", never "saved it", and the handed-back proposal waits for you instead of failing every tick (G650). A second proposal of the same value for one fact is folded under the first one's card but is its own item, judged by these same rules (G600). An assistant's open question or take-back (`open_question`, a retirement) is not a fact, and only a conflict asks you: under file all it is set aside on the next tick (rejected by `auto-decide`), with a diary line ("A question about Course B was set aside, since only a conflict asks you") and Undo on Settings; the assistant can raise it again. A capture's question or retirement, and your own, still wait as above (audit v5, midday: 4 of the Gardener's questions and 2 of the capture agent's private pages sat as asks with no way out).

Adding to a set (another phone) or a dated fact (`max`) is never a conflict, and neither is a newer value in a run from a source as strong as the one it follows. Undo works as for any decision: it takes the fact back out and it waits for you for good. An assistant's own proposals keep their own rule (they expire after `proposal_days`). An old fact, a past date or an old next step is never asked (G452): none is a conflict, so it stays in the Brain's "To recheck", upkeep's `past-date` finding and the trust audit. `bun scripts/filing-counts.ts` prints, counts only, why each open proposal is still open (the hub's fixed words, or the write checks that refused a save).

A fact dated after today (a mail about next week) is saved as of today, as when you accept it by hand, unless it replaces a different current value: then it waits, since filing it today would end the current value now. A save the write path refused waits for a day (nothing promises it will file), then tried again, or at once when the hub runs other code (a deploy may carry the fix); refused twice under the same code, it isn't tried again until other code runs, and waits as a card that the self-check's `auto_saves` line counts (G519). A yes to an assistant's proposal that also asks to move its page to another area, the hub's or yours, files its fact where the page is, whether it named the page by id or by title: no path moves a page's area, and an assistant never does (G519, G522; before, the write handed it back to the inbox and the hub's save was refused every day). A filing whose value the page already held (the same write again, or one more source for it) leaves one diary line, "confirmed by another email", whose Undo takes the added source out; the self-check's `filed_lines` line warns when a filing in the last day left no diary line (G524). A proposal quoted from a mail's footer ("sent to <address>", unsubscribe) is dropped by the hub with Undo; new ones are never proposed.

#### Conflicts wait for the Gardener

The owner's rule (2026-10-25): "ask me only conflicts caught by the gardener". A capture or pull that gives a different value for a fact the brain holds (`merge: replace`, unless it is newer and every value it replaces came from the same kind of source: the calendar updating what the calendar said, which files as an update), or a different value in a run of values (`merge: latest`, such as a next step after `pocketbrain next-steps newest`) that the write path wouldn't keep as simply newer or older (the held value came from a stronger source, such as your word against a capture, or a guessed value against an exact one, or both are dated the same day with no numbers to order them), is filed as a conflict by `auto-decide`: the live value stays on the note and is what every assistant reads, the other side waits in the conflict's packet beside it (`contested: <id>` on the live record, G425; a fact an older hub froze as `{ dispute, candidates }` while it waited gets its live value back, the packet's first side, when the hub starts: `unfreezeHeld` in `src/write.ts`, one hub commit with a why, G428; on a page that holds a private fact the conflict waits for you in the inbox instead (asked on the home, `inboxConflicts` in `src/settle-inbox.ts`), since the write hands it to you, and a capture an older hub answered accepted there with nothing saved goes back to the inbox when the hub starts: `reopenLostAccepts`, one hub commit with a why, G431; it comes back as its writer's, and not at all when the write's hand-back to you already waits on that page, G601, or when the page holds the value in other words, as the write compares it; it goes back once, then waits for you and the hub never files it again, and the self-check's `redecided` line warns when the hub decides one proposal more than once in a week, G742), nothing is replaced until someone picks, and "Filed for you" says "held it as a conflict" with Undo (the proposal comes back and the conflict goes). The row says what the write did, not what filing expected: when the write path updates the value instead (a newer value from as strong a source), the row says "saved it", and only a write that opened a conflict is logged as one (G438). Until the hub's tick files it, a capture's inbox record is not an ask anywhere: not on the home page, the digest or in the north star's asks. Once filed, its record in `inbox/decided/` carries `by: auto-decide` and `filed: by the hub's write path with Undo; nobody approved it`, so it never reads as your approval (G440). The conflict's packet carries `gardener_first` (the time it opened), and it stays off the home page and the text channel until the Gardener has been by (`openItems` in `src/textline/items.ts`):

When the filing tick files a newer value as an update (every value it replaces came from the same kind of source), the write agrees even if the older value was found in its email (`verified-by-source`) and the newer one not yet: it updates, and the older value goes to history (`sameKindNewer` in `src/write.ts`, G513). Before, every newer email about such a fact opened a conflict. An older email still never replaces a newer one, and an assistant's own newer claim against a verified value is still a conflict.

A conflict is two values that can't both hold (owner's phone, 2026-11-03, G662: "this is not 1 or the other"; and 2026-11-06, G674 to G677). These never ask:

- **The same sentence in other words.** Values of five words or more are compared without what only shapes a sentence (`valueKey` in `src/normalize.ts`): case, accents, punctuation, articles and "is"/"are" don't count, and "to be retained" reads as "to retain" (only the passive side is rewritten, so a name after "to" is never touched, and a verb ending in "e" such as "to move" and "to be moved" stays two values), so the same sentence from two mails merges into one fact with both sources (step 1). A plural alone folds too ("exam", "exams"), on a word written in lower case inside the sentence, since both can hold and nothing is asked; a word with a capital, so a name, and the sentence's first word never do. Every other word stays whole (audit v13, G759): a name and a longer name ("Robert", "Roberts"), tense ("expires", "expired"), numbers, negations ("not"), a sign ("-740", "740") and a currency ("$740", "€740") are different values, and a different value is a conflict to settle, never a source merged into the first. Shorter values keep the exact comparison, with the sign and the currency.
- **One sender, one day.** Two items the hub pulled itself from the same sender on the same day, of the same kind of source, are the fact changing that day: the later one updates and the earlier goes to history (step 4). A pulled item's capture record keeps its sender as a key (`sender_key`, a hash of the address, never the address; `senderKey` and `oneSender` in `src/capture.ts`), and the write asks for that key on both sides, so an item pulled before G662 (no key) still opens a conflict. Two senders saying different things the same day are a conflict, as are money, health and legal values of the same day.
- **The same long sentence, its parts in another order.** A value of ten words or more said again with a clause moved and a filler word or two more ("…for each client you want to retain") is the same value (`nearSame` in `src/normalize.ts`, G678): one side's words, stemmed, are all in the other, the other adds at most three words that only address the reader ("you", "want" beside "you", "please"; never "all", "any", "each" or "need"), most of the shorter one's words come in the same order, and numbers and negations match. The same words merely reordered never fold, since that can swap who does what.
- **A page by another name.** A field that links to a page (`normalize: link`, such as a person's org) takes a name the way it takes the link: "LAKEVIEW College", "lakeview  collège" or "[[Lakeview college]]" is the page whose title or alias that is, when exactly one page the writer is shown has it (`pageLink` in `src/write.ts`), so it merges with the link the page already holds (G674). A page the writer can't see never resolves; the name stays a name.
- **One mail, two values.** Two values for one fact from the very same item of one day (one mail: sign the agreement, and the interview on Thursday) both hold, so both stay, in one value joined by "; " (step 4, G675), up to four parts. The same item read again adds nothing. Money, health and legal values still ask.
- **An assistant's word against yours.** A value whose only source is an assistant's own word or memory (`agent:`, `instinct-mem:` and the like) never asks against the owner's word, whatever its date: the owner's value stays and the assistant's goes to history (step 6, G677). A mail or event the hub can check, of the same day or later, may say the fact changed, and that still asks, as does a money-, health- or legal-shaped value from an assistant (an owner's correction relayed through a chat is cited as the assistant's word too).
- **A newer mail in a run of values.** In a run (`merge: latest`, such as next steps), a newer pulled mail is the next value even when the older one was found in its mail (`verified-by-source`), as G513 already did for `merge: replace`.

**Not sure, keep both** sticks (G676). Once the owner answers it on two values, the same two never open a conflict again on that fact, from any source: the other value joins history beside the live one (`keptBothWith` in `src/write.ts`). A third value still asks. A proposal the owner turned down (Keep yours, or keep both on a conflict that waited in the inbox) is not proposed again by the same assistant with the same value, unless it cites a source the turned-down one didn't; only the writer's own proposals count, so the reply tells it nothing about anyone else's. The nightly upkeep lists any open conflict on two values the owner already kept both of (`asked-again-after-keep-both`, report-only), so a way round this shows up the next morning.

Conflicts opened before G662 whose sides both hold are listed by the nightly upkeep, report-only, under "To review" in its run's findings (`both-hold-conflict`, `bothHold` in `src/upkeep.ts`): nothing is settled or closed, so the count says how many old cards are false before anything is turned on.

Only what the hub pulled itself (a capture's proposal) files as such an update. When the filing tick says yes to an assistant's own proposal, nobody approved it: from outside the assistant's areas a different value is weighed as the assistant's own write would be (a conflict unless it is a newer value from as strong a source), and the assistant's word for what a mail says never updates a verified value. Before, naming any other area on a remember made the write an area-change proposal, the tick's yes dropped the area and skipped that weighing, and the contradiction filed as an update (audit v6, G536; the row in `test/contracts/write.contract.test.ts`). The tick's yes also keeps the assistant's own view: a fact hidden from it, its paused or read-only switch and a type it isn't given stop the write as they would its own (G539).

- the Gardener suggested a side (`suggest_answer`): the settle screen leads with its pick and its one line why;
- or a Gardener pass read the open conflicts after this one opened (`open_disputes`) and had nothing to say;
- or 36 hours passed (`GARDENER_WAIT_H`), so a night without a pass never hides it for good.

One that reads like money, health or legal asks the same day, its values behind Show it. A conflict an assistant's own write opened is not held. The trade is a night's delay for most conflicts. `bun scripts/filing-counts.ts` counts them (filed from a capture, suggested on, waiting, asked on the home, after 36 hours), and for each proposal still open over a different value how the held value compares (stronger, as strong or weaker source; older, same day or newer; rechecked), counts only. Another value for that fact joins the waiting conflict (nothing replaces the live value meanwhile) and stays held with it. The resolver doesn't see a held conflict either, so nobody settles it before the Gardener has been by, and the daily digest lists a conflict only once the Gardener has been by (or it is money, health, legal or private), never printing a private, money, health or legal one's values. A conflict with your own word also keeps your value live while it asks. When the hub saves a fact that changed since it was weighed (two captures on one fact in one tick), the second is read against the first and waits as a held conflict, logged as one.

An assistant's proposal whose reason reads like health, money or legal keeps that reason behind Show it, with the value, even on a note that isn't private: a Gardener sensitivity review names what it found. The daily digest prints neither for such a proposal, and the text channel sends it as a change to a private note.

### Saved for you

Sources keep the brain fresh without you: the pile of calendar and mail proposals grew faster than anyone clears it, so what they say about your projects and plans can stop waiting for a swipe. It is off until you turn it on: add `source_saves_per_day: 20` under `auto_decide:` in rules/escalation.yaml. Until then each such proposal waits on Settings' Needs a look list. Once on, a proposal is saved for you when all of these hold (`saveVerdict` in `src/filing.ts`):

- A calendar or mail pull wrote it (`gcal:`, `gmail:` or `mail:` refs, and the `capture:` field only the pull pipeline writes). Texts, transcripts, chat and documents still wait for you.
- It isn't about a person (a person note, a `people/` id, or a new person), and the source names what it's about (no proposal whose entity the model inferred). A new note's name that now matches a person, money or private note waits too, since the save would land there.
- It isn't private, money, health or legal: not on a private or money note, not from a source with a private floor, and nothing in its value, its note's name or the source's words reads that way (the same `sensitiveShape` as expiry, English and French).
- It cites none of your word, and it adds a fact or a newer value: no retirement, no open question.
- It doesn't change a value you confirmed, or one another kind of source gave (the calendar can update what the calendar said), and it is newer than the value it replaces. Anything else would be a conflict, and conflicts are yours.

A saved fact is the source's word, never yours: it keeps its own refs and verification, and the commits are by `auto-decide`, not you. It goes through the same write checks as your Accept. A fact the hub will save, today or once the daily cap turns, isn't listed as open: Settings says how many, and each shows in "Filed for you" once saved. One you undid waits for you for good.

A deadline never starts before the hub first saw the item (`log/filing-seen.json`; a `log/deck-seen.json` from before the deck was removed is moved there on first read, so running deadlines carry on), so a proposal older than this feature still gets its full `proposal_days`. While an item can't be decided (deciding is off, its assistant is paused) that clock is cleared, so once it can be it gets the full notice again. No assistant may be named `auto-decide` or `hub`: the policy won't load and `pocketbrain add` refuses it, because those names mark the hub's own commits (G426).

`pocketbrain filing now` runs the same step by hand, only when the hub isn't running on this machine (it refuses if the health URL answers). Every process that decides, the hub's tick or `filing now`, first takes one lock file (`.git/pocketbrain-decide.lock`, `src/filelock.ts`), so two never settle the same item at once: while one holds it, another decides nothing that round (`filing now` says another process is deciding). A lock left by a process that died, or older than 10 minutes, is taken over.

### Settings (rules/escalation.yaml, owner only)

```yaml
auto_decide:
  off: false          # true: the hub never decides; everything waits for you (conflicts always do)
  proposal_days: 14   # an unanswered proposal expires after this; at least 3
  source_saves_per_day: 0    # off (the default); 20 saves up to 20 low-risk calendar and mail facts a day for you
  # file: all               # every capture and source fact files itself; only a conflict asks (pocketbrain filing all on)
```

`auto_decide` must be a map. Anything else (`auto_decide: off`, `false`, a list) means off.
